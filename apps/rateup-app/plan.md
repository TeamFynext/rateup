# RateUp Android App Optimization Plan

Target: pass Google Play's new App Optimization requirements (25% minimum R8
coverage across optimization / shrinking / obfuscation, enforced February 2027),
reduce the 51.5 MB uncompressed DEX, get ahead of the dynamic-memory and
bitmap-memory thresholds, and clean up the duplicated brand icons in
`assets/images`.

Sources:

- https://docs.expo.dev/versions/latest/sdk/build-properties/
- https://android-developers.googleblog.com/2026/08/app-quality-memory-optimization-secure-onboarding.html

This document is written so an agent can execute it end to end. Every step
says what to change, why, and how to verify.

---

## 0. Ground rules for whoever executes this

1. **`android/` and `ios/` are gitignored** (see `.gitignore`). They are
   regenerated by `npx expo prebuild`. Never hand-edit files under `android/`
   as a fix. Every native change must be expressed in `app.json` or in a
   config plugin under `plugins/` so it survives prebuild and EAS builds.
2. **Stack facts** (verified in the repo, do not re-derive):
   - Expo SDK 57, React Native 0.86.0, Hermes on, New Architecture on.
   - RN 0.86 pins AGP 8.12.0 via `node_modules/react-native/gradle/libs.versions.toml`.
     Do **not** force AGP 9.0. The Play Console hint "Upgrade to AGP 9.0" is
     about R8 metadata reporting only. It is not required to hit the 25%
     coverage thresholds, and RN 0.86's Gradle plugin is not compatible with
     AGP 9.
   - R8 full mode is already the default on AGP 8.x. No flag needed.
   - 16 KB page size is already supported. Nothing to do.
   - `expo-image` is **not** installed (earlier conversation claimed it was;
     that was wrong). Step 5 installs it.
3. Build with EAS: `eas build -p android --profile preview` for the test AAB,
   `--profile production` for release. Both run prebuild from `app.json`.
4. Commit after each phase with a conventional-commit message so phases can be
   reverted independently.

## 1. Why the Play scores are what they are (root causes)

| Play Console row        | Current | Root cause in repo                                                                                                                                                                                                                      |
| ----------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Obfuscation percentage  | 1%      | The `enableMinifyInReleaseBuilds` / `enableShrinkResourcesInReleaseBuilds` flags in `app.json` lines 59-64 are **uncommitted working-tree changes**. Every build Play has analyzed was built with R8 off.                               |
| Shrinking percentage    | –       | Same as above.                                                                                                                                                                                                                          |
| Optimization percentage | –       | Even with minify on, the Expo/RN template's release block uses `getDefaultProguardFile("proguard-android.txt")`, which contains `-dontoptimize`. Optimization stays at 0 until the file is switched to `proguard-android-optimize.txt`. |
| R8 configuration        | –       | Requires AGP 9.0 metadata. Out of scope until React Native adopts AGP 9. Ignore.                                                                                                                                                        |
| Total uncompressed DEX  | 51.5 MB | No shrinking at all, plus heavy native deps (Media3 via react-native-video, Play Services via Google Sign-In, Firebase Messaging via expo-notifications).                                                                               |

## 2. Phase A: turn on R8 correctly (biggest win, do first)

### A1. Commit the existing build-properties flags, unchanged

`app.json` already contains (uncommitted):

```json
[
  "expo-build-properties",
  {
    "ios": { "useFrameworks": "static" },
    "android": {
      "enableMinifyInReleaseBuilds": true,
      "enableShrinkResourcesInReleaseBuilds": true,
      "extraProguardRules": "-keepattributes SourceFile,LineNumberTable\n-renamesourcefileattribute SourceFile"
    }
  }
]
```

Keep exactly that. Decisions that are deliberate:

- **Do not** set `enableBundleCompression: true`. It shrinks the download but
  forces the Hermes bytecode to be inflated into anonymous RSS at startup
  instead of being mmapped from the APK. That directly hurts the new
  dynamic-memory metric.
- **Do not** set `useLegacyPackaging: true` for the same reason (native libs
  would be extracted instead of mmapped).
- Leave `enablePngCrunchInReleaseBuilds` at its default (`true`).
- Keep the two `-keepattributes` lines. They keep crash stack traces
  readable and do not reduce obfuscation coverage.

### A2. Add a config plugin that enables R8 optimization

Create `plugins/withR8Optimize.js`:

```js
const { withAppBuildGradle } = require("expo/config-plugins");

/**
 * The RN/Expo template ships `proguard-android.txt`, which contains
 * `-dontoptimize`. Play's "Optimization percentage" stays at 0 with it.
 * Swap to the optimize variant so R8 inlines, removes dead branches, etc.
 */
module.exports = function withR8Optimize(config) {
  return withAppBuildGradle(config, (config) => {
    const from = 'getDefaultProguardFile("proguard-android.txt")';
    const to = 'getDefaultProguardFile("proguard-android-optimize.txt")';
    if (!config.modResults.contents.includes(from)) {
      throw new Error(
        "[withR8Optimize] Could not find proguard-android.txt in app/build.gradle. " +
          "The template changed; update the plugin.",
      );
    }
    config.modResults.contents = config.modResults.contents.replace(from, to);
    return config;
  });
};
```

Register it in `app.json` `plugins`, **after** `expo-build-properties`:

```json
"./plugins/withR8Optimize.js"
```

Verify locally:

```sh
npx expo prebuild -p android --clean
grep -n "proguard-android-optimize" android/app/build.gradle
grep -n "enableMinifyInReleaseBuilds\|enableShrinkResources" android/gradle.properties
```

All three must show the expected values.

### A3. ProGuard keep rules: add only what is proven necessary

Start with **no** additional rules beyond the two keepattributes lines.
Every library in the stack ships consumer ProGuard rules that R8 merges
automatically (Reanimated, Worklets, RN core, Expo modules, Firebase, Play
Services, Media3). Adding `-keep class x.** { *; }` wildcards lowers the
obfuscation percentage and is the most common reason apps get stuck near
the 25% floor.

If, and only if, the Phase A4 test build crashes with a
`ClassNotFoundException` / `NoSuchMethodError` / reflection failure, add the
narrowest rule for that class to `extraProguardRules`. Likely suspects,
in order:

1. SuperTokens (`supertokens-react-native`) is pure JS, no rule needed.
2. Google Sign-In: rules ship with `play-services-auth`. Usually nothing.
3. `expo-notifications` Firebase service: shipped rules. Usually nothing.
4. Any class the app references from `AndroidManifest.xml` is kept
   automatically by AGP.

### A4. Ship an R8 build to internal testing and read the numbers

```sh
eas build -p android --profile preview
```

Install on a physical device (not just an emulator) and exercise every
native path that obfuscation can break:

- Cold start, warm start, background/foreground.
- Email/password sign-in, Google sign-in, Apple sign-in (Android shows the
  web flow), sign-out, session restore after kill.
- Push notification receipt in foreground, background, and killed state.
  Tap-through deep link via `rateup://`.
- Video playback (`react-native-video`) in a chat message.
- Audio record + playback (`expo-audio`).
- Document picker, file share, SQLite read/write, clipboard, haptics.
- Charts (`react-native-gifted-charts` + `react-native-svg`).
- Keyboard controller on chat footer, pager view, tab view.

Then upload to Play internal testing and wait for the App Optimization card
to refresh (typically 24 to 48 h). Expected:

| Row                     | Expected after Phase A |
| ----------------------- | ---------------------- |
| Optimization percentage | 40 to 70%              |
| Obfuscation percentage  | 60 to 80%              |
| Shrinking percentage    | 40 to 60%              |
| Uncompressed DEX        | roughly 25 to 35 MB    |

EAS uploads `mapping.txt` automatically for AAB builds. Confirm in
Play Console > App bundle explorer > the build > "Deobfuscation file" says
uploaded. If it is missing, crash reports become unreadable.

### A5. Commit

```
feat(android): enable R8 minify, shrink, and optimization for release builds
```

## 3. Phase B: reduce DEX size further

Do this only after Phase A numbers are in, so each change is attributable.

### B1. Measure what remains

Download the AAB from EAS, open it in Android Studio > Build > Analyze APK.
Sort `classes*.dex` by package size. Record the top 10 in the PR description.

### B2. Trim react-native-video's Media3 extensions

`react-native-video` v6 defaults to compiling in SmoothStreaming, DASH and
HLS. RateUp plays MP4/HLS-style chat attachments. Add the plugin to
`app.json` with only what is used (confirm with backend which stream
formats exist; if only progressive MP4 and HLS, use this):

```json
[
  "react-native-video",
  {
    "enableNotificationControls": false,
    "enableADSExtension": false,
    "androidExtensions": {
      "useExoplayerRtsp": false,
      "useExoplayerSmoothStreaming": true,
      "useExoplayerDash": true,
      "useExoplayerHls": true
    }
  }
]
```

Verify video still plays in `src/components/chatDisplay/chatBody/messageBubbleTypes.tsx`
and `src/components/webform/HappyIndex.tsx`.

**DASH and SmoothStreaming must stay `true`, despite being unused.** Turning an
extension off does not drop those classes from the app — it makes
`react-native-video` compile its own no-op stubs at the real Media3 package
names (`android/src/main/java/androidx/media3/exoplayer/dash/...`). Its
`sourceSets` block excludes those stubs only when the extension is _enabled_
(`node_modules/react-native-video/android/build.gradle`, the
`if (ExoplayerDependencies["useExoplayerDash"]) { exclude ... }` blocks).

`expo-audio` pins `androidxMedia3Version = "1.9.0"` and pulls
`media3-exoplayer-dash` and `media3-exoplayer-smoothstreaming`
unconditionally, so the real classes are on the classpath either way. With the
extensions off, `androidx.media3.exoplayer.dash.DashMediaSource$Factory` is
defined twice and `:app:minifyReleaseWithR8` fails with "Type ... is defined
multiple times". Debug builds do not run R8, which is why this only surfaced on
an EAS release build.

RTSP and IMA stay off: `expo-audio` does not pull those two, so their stubs are
the only copy and no collision occurs.

### B3. Remove `react-native-paper`

It is imported in exactly one place (`ProgressBar` in one component). It is
JS-only so it does not affect DEX, but it is a large JS dependency for one
progress bar and pulls its own theme provider. Replace with a 10-line
`View`-based progress bar (or the existing `react-native-circular-progress`
if a ring is acceptable) and `npm uninstall react-native-paper`.
Low priority; skip if time is short.

### B4. Leave these alone

- Google Sign-In, Firebase Messaging, expo-sqlite, Reanimated, Worklets,
  Screens: all required, all already shrink well under R8.
- `buildArchs`: Play splits AABs per ABI automatically. No change.

## 4. Phase C: brand icon consolidation (`assets/images`)

### C1. What is there today

| File                    | Dimensions | Alpha               | Content bbox                                            | Used by                                                                       | Verdict                                                                                                                                                                |
| ----------------------- | ---------- | ------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `icon.png`              | 1024×1024  | opaque (white fill) | full canvas                                             | `expo.icon` (iOS App Store icon)                                              | **Keep.** Apple requires an opaque 1024 icon.                                                                                                                          |
| `adaptive-icon.png`     | 1024×1024  | transparent         | 242..782 (540 px, inside the 66% safe zone)             | `android.adaptiveIcon.foregroundImage`                                        | **Keep.** Android needs transparent + safe-zone padding.                                                                                                               |
| `splash-icon.png`       | 1024×1024  | transparent         | 102..921                                                | **only** `src/app/auth/SignIn.tsx` at 64×64                                   | **Delete.** Not used by the splash plugin at all. Decoding a 1024² PNG (4 MB bitmap) to draw a 64 pt icon is the exact pattern the new bitmap-memory metric penalises. |
| `logo.png`              | 2500×992   | transparent         | 289..2215 × 297..760 (1926×463 of content, 60% padding) | `expo-splash-screen.image` with `imageWidth: 200`                             | **Keep but shrink.** Source is ~4× larger than needed and mostly empty margin.                                                                                         |
| `favicon.png`           | 48×48      | transparent         | –                                                       | `web.favicon`                                                                 | Keep. Web only.                                                                                                                                                        |
| `notification-icon.png` | 96×96      | white silhouette    | –                                                       | `expo-notifications.icon`                                                     | **Keep.** Android requires a white-on-transparent silhouette; cannot be shared with anything else.                                                                     |
| `signinpage-icon.svg`   | vector     | –                   | –                                                       | exported as `RateLogo` in `src/constants/imageExports.ts`, **zero consumers** | Reuse it: this is the vector star mark and should replace `splash-icon.png` in SignIn.                                                                                 |
| `google-icon.svg`       | vector     | –                   | –                                                       | `googleSignInScreen.tsx`                                                      | Keep.                                                                                                                                                                  |

### C2. Answer to "can we use one file everywhere?"

No, one **file** cannot serve every slot, because the platforms impose
mutually exclusive requirements: iOS wants opaque, Android adaptive wants
transparent with safe-zone padding, notifications want a white silhouette.
But one **source** can generate all of them, and the in-app usage should be
a vector, not any of the PNGs.

Target layout:

```
assets/
  brand/
    star-mark.svg          <- single source of truth (move signinpage-icon.svg here)
  images/
    icon.png               <- generated: 1024, opaque #FFFFFF, mark scaled to ~70%
    adaptive-icon.png      <- generated: 1024, transparent, mark scaled to ~52% (safe zone)
    notification-icon.png  <- generated: 96, white silhouette of mark
    splash-logo.png        <- generated from the full wordmark, trimmed, 800 px wide
    favicon.png            <- generated: 48, transparent
    google-icon.svg        <- unchanged
```

### C3. Steps

1. Move `assets/images/signinpage-icon.svg` to `assets/brand/star-mark.svg`.
   Confirm visually that it is the star-with-pin mark (viewBox `30 -3 56 55`).
   If it turns out to be a different artwork, export the star mark as SVG
   from the design file instead; do not proceed with a PNG source.
2. Update `src/constants/imageExports.ts`:
   ```ts
   import StarMark from "@/assets/brand/star-mark.svg";
   import GoogleIcon from "@/assets/images/google-icon.svg";
   export { StarMark, GoogleIcon };
   ```
3. In `src/app/auth/SignIn.tsx` replace the `<Image source={require(".../splash-icon.png")} .../>`
   block with `<StarMark width={64} height={64} />` and delete the comment
   about the PNG. Vector renders identically on light and dark backgrounds,
   which was the original reason the PNG was chosen.
4. Delete `assets/images/splash-icon.png`.
5. Add `scripts/generate-brand-assets.mjs` using `sharp` (devDependency):
   - Rasterise `star-mark.svg` to 1024 with a white background for `icon.png`.
   - Rasterise to 1024 transparent, mark occupying the centre 540 px, for
     `adaptive-icon.png` (matches the current file's bbox).
   - Rasterise to 96, flatten all colour to `#FFFFFF`, keep alpha, for
     `notification-icon.png`.
   - Rasterise to 48 transparent for `favicon.png`.
   - For the splash: take the current `logo.png`, `trim()` transparent
     margins, resize to 800 px wide (200 dp × 4 for xxxhdpi), add 10%
     padding, save as `splash-logo.png`. Update
     `expo-splash-screen.image` to point at it. Keep `imageWidth: 200`.
     Add `"brand:assets": "node scripts/generate-brand-assets.mjs"` to
     `package.json` scripts. Commit the generated PNGs (EAS does not run the
     script).
6. Run `npx expo prebuild -p android --clean` and check
   `android/app/src/main/res/mipmap-*/` and `drawable-*/splashscreen_logo.png`
   are produced with sensible sizes. Run the app once and eyeball the
   launcher icon, splash, and sign-in screen.
7. Commit:
   ```
   chore(assets): single-source brand mark, vector star on sign-in, trimmed splash logo
   ```

Expected memory effect: the sign-in screen no longer allocates a 4 MB bitmap
for a 64 pt icon, and the splash decodes a ~1 MB bitmap instead of ~10 MB.

## 5. Phase D: memory readiness (same February 2027 deadline)

The Play post adds two metrics not yet visible on the card: dynamic memory
(anonymous RSS + swap) and bitmap memory. Do this after Phases A to C.

### D1. Install `expo-image` and migrate `react-native` `Image` usages

```sh
npx expo install expo-image
```

Files currently importing `Image` from `react-native` and rendering it
(migrate each; keep `resizeMode` → `contentFit` mapping in mind):

- `src/app/auth/SignIn.tsx` (goes away in Phase C)
- `src/app/protected/flow/flow2/[flowresponseId].tsx`
- `src/components/chatBox/ChatBox.tsx`
- `src/components/chatDisplay/chatBody/messageBubbleTypes.tsx`
- `src/components/chatDisplay/chatFooter/MessageSendPanel.tsx`
- `src/components/chatDisplay/chatFooter/templates/TemplateComponents.tsx`
- `src/components/flow/ImageResponse.tsx`
- `src/components/home/Account.tsx`

Why: `expo-image` downsamples remote and local bitmaps to the view size,
shares a disk + memory cache with an LRU cap, and releases bitmaps when the
view is off-screen. That is precisely what the bitmap-memory threshold
measures. For chat images, also pass `recyclingKey={message.id}` inside
FlashList rows.

### D2. Audit stores for lingering buffers

`base64-js` and `buffer` are in dependencies. Grep `src/store` and
`src/utils` for base64 strings, `Buffer.from`, or audio `Uint8Array`s held
in Zustand. Anything kept after upload/playback completes must be cleared
in the screen's unmount effect. Document findings in the PR; fix the obvious
ones.

### D3. Verify

On a physical mid-range device, `adb shell dumpsys meminfo com.rateupapp.rateup`
before and after scrolling a long image-heavy chat, then after backgrounding
for 60 s. Record "TOTAL PSS" and "Graphics" rows in the PR. Bitmap memory
should drop noticeably after backgrounding.
